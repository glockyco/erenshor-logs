# Mod Audit — 2026-05-17

## Scope and evidence

This audit covers the BepInEx mod implementation in `mod/src`, mod tests in
`mod/tests/ErenshorLogs.Tests`, current project docs, current decompiled main and
playtest game scripts under `reference/game-source/{main,playtest}`, and public
BepInEx/Harmony/Unity/Thunderstore guidance.

Observed reference game builds:

- Main: Steam app `2382520`, build `22374607`.
- Playtest: Steam app `3090030`, build `23258843`.

Verification run during the audit:

```text
cd mod && dotnet test tests/ErenshorLogs.Tests
Passed!  - Failed: 0, Passed: 99, Skipped: 0, Total: 99
```

Existing warnings were IDE0005 unnecessary-using warnings in mod files. No
runtime in-game validation was performed in this audit.

## Executive summary

The mod has a solid core for live damage logging: BepInEx startup, Harmony patch
wiring, Newtonsoft.Json protocol serialization, WebSocket broadcasting, session
management, actor identity, combat relevance filtering, and damage attribution
through ability/effect context are all present and tested at the unit level.

The major gap is that the public schema and docs describe a full combat-log
system, while the mod currently emits only raw damage and combat-boundary events.
Healing, resource, death, status lifecycle, interrupt, reflect, proc/resonance,
pet classification, mitigation, and overkill fields are either absent or only
represented in schema types. Several project docs also describe older designs
that no longer match the code.

The highest-priority correctness risks are:

1. Actor registry state is never cleared between sessions.
2. Ability context finalizers can pop an outer context when their prefix did not
   push anything.
3. Combat start ordering is backwards in the event stream for auto-started
   sessions: the triggering damage event is queued before the synthetic
   `combatStart` event.
4. WebSocket binds to all network interfaces by default.
5. Status-effect tracking misses common 3-parameter `Stats.AddStatusEffect`
   call sites, including playtest spell/group effects.

## What is already implemented

### BepInEx/Harmony host

- `Plugin` is a `BaseUnityPlugin` with `[BepInPlugin]` metadata
  (`mod/src/Plugin.cs:19-20`).
- Services are registered once at startup (`Plugin.ConfigureServices`) and
  disposed in `OnDestroy` (`mod/src/Plugin.cs:189-258`).
- Harmony is instantiated with the plugin GUID, patches are applied with
  `PatchAll`, and `UnpatchSelf` is called on teardown
  (`mod/src/Plugin.cs:37-42`, `mod/src/Plugin.cs:252-257`).
- The mod targets `netstandard2.1`, has nullable enabled, and uses
  Newtonsoft.Json (`mod/ErenshorLogs.csproj:3-47`).

### Live protocol and serialization

- WebSocket protocol messages exist for handshake, session start, session end,
  and batched combat events (`mod/src/Protocol/Messages.cs`).
- JSON settings use camelCase properties and camelCase enum strings through
  Newtonsoft.Json (`mod/src/Json/JsonSettings.cs`).
- The web schema agrees with the mod on camelCase event names such as
  `damagePhysical`, `healSpell`, and `combatStart`
  (`web/src/lib/types/schemas.ts:10-38`).

### Session lifecycle

- Automatic sessions start lazily from configurable event types
  (`SessionManager.OnCombatEvent`, `mod/src/Session/SessionManager.cs:80-95`).
- Automatic sessions end on inactivity and backdate the end time to the last
  keep-alive event timestamp (`mod/src/Session/SessionManager.cs:98-119`).
- Manual session start/stop hotkeys are implemented in `Plugin.Update`
  (`mod/src/Plugin.cs:60-97`).
- Session boundary events are emitted as synthetic `CombatEvent`s
  (`mod/src/Session/SessionManager.cs:158-213`).

### Damage capture

Current production emitters are limited to these event types:

- `Character.DamageMe` -> `damagePhysical`
  (`mod/src/Hooks/DamageMePatch.cs:12`, `mod/src/Hooks/DamageMePatch.cs:171-194`).
- `Character.MagicDamageMe` -> `damageMagic`
  (`mod/src/Hooks/MagicDamageMePatch.cs:131-132`).
- `Character.BleedDamageMe` -> `damageDot`
  (`mod/src/Hooks/BleedDamageMePatch.cs:159-160`).
- `Character.EnvironmentalDamageMe` -> `damageEnvironmental`
  (`mod/src/Hooks/EnvironmentalDamageMePatch.cs:98-99`).
- `SessionManager` emits `combatStart` and `combatEnd`
  (`mod/src/Session/SessionManager.cs:168-191`).

The current main and playtest decompiles both contain the primary patched damage
methods with compatible signatures, including `DamageMe`, `MagicDamageMe`,
`BleedDamageMe`, and `EnvironmentalDamageMe`.

### Ability and effect attribution

- `UseSkill.DoSkill` and `UseSkill.DoSkillNoChecks` push skill context
  (`mod/src/Hooks/DoSkillPatch.cs`, `mod/src/Hooks/DoSkillNoChecksPatch.cs`).
- `SpellVessel.ResolveSpell` pushes spell context
  (`mod/src/Hooks/ResolveSpellPatch.cs`).
- `WandBolt.DeliverDamage` pushes wand/bow auto context
  (`mod/src/Hooks/DeliverDamagePatch.cs`).
- Several boss/area-effect update hooks push area-effect context
  (`mod/src/Hooks/AEEventUpdatePatch.cs`, `AEEvent2UpdatePatch.cs`,
  `AstraBreathScriptUpdatePatch.cs`, `NPCFightEventBreathAttackPatch.cs`,
  `SableheartEventUpdatePatch.cs`).
- `EffectTracker` and `TickEffectsSlotTracker` attempt to map DoT/HoT ticks back
  to status-effect slots (`mod/src/Context/EffectTracker.cs`,
  `mod/src/Context/TickEffectsSlotTracker.cs`).

The recent `DoSkillNoChecks` patch is important: playtest SimPlayers use
`UseSkill.DoSkillNoChecks`, and the current playtest decompile still contains
that method.

### Actor identity and combat relevance

- `ActorRegistry` assigns stable actor references for player, simulated players,
  NPCs, and pets (`mod/src/Registry/ActorRegistry.cs`).
- `ActorTypeResolver` classifies player, pets, SimPlayers, then NPCs
  (`mod/src/Registry/ActorTypeResolver.cs`).
- `CombatRelevanceChecker` includes player, group members, pets, aggro table,
  group target, and engaged-NPC relevance paths
  (`mod/src/Hooks/CombatRelevanceChecker.cs`).
- `CombatRelevanceCheckerAdapter` uses reflection for playtest-only
  `NPC.MyRaidSlot`, preserving compatibility with main where the field does not
  exist (`mod/src/Hooks/CombatRelevanceCheckerAdapter.cs:10-12`,
  `mod/src/Hooks/CombatRelevanceCheckerAdapter.cs:69-72`).

### Test coverage already present

The mod has unit tests for:

- Event and enum serialization.
- Protocol message serialization.
- Event emitter behavior.
- Actor registry identity/master behavior.
- Session manager lifecycle.
- Combat relevance fallback behavior.
- Generic combat event builder behavior.
- A limited patch-presence regression for `DoSkillNoChecksPatch`.

## Missing or incomplete features

### P0 — schema-promised events that are not emitted

`EventType` defines damage, healing, resource, status, death, interrupt, and
combat-boundary values (`mod/src/Events/EventType.cs:7-89`), but production
source references to `EventType.` show only `DamagePhysical`, `DamageMagic`,
`DamageDot`, `DamageEnvironmental`, `CombatStart`, and `CombatEnd` are emitted.

Missing emitted event families:

- Healing: `healSpell`, `healHot`, `healLifesteal`, `healRegen`.
- Resources: `manaUse`, `manaRestore`, `manaRegen`.
- Status lifecycle: `buffApply`, `buffRefresh`, `buffFade`, `debuffApply`,
  `debuffRefresh`, `debuffFade`.
- Death: `death`.
- Interrupts: `spellInterrupt`.
- Damage shield/reflection: `damageReflect`.
- Proc and resonance attribution: `damageProc`, `ability.procSource`,
  `flags.resonating`.
- Pet-damage classification: `damagePet` and `flags.pet`.
- Semantic physical damage split: `damageMelee`, `damageSkill`, `damageSpell`.

Relevant current playtest methods/call sites exist for these families:

- `Stats.HealMe(int)` and `Stats.HealMe(Spell, int, bool, bool, Character)`.
- `Stats.ReduceMana(int)`.
- `CastSpell.InterruptCast()`.
- `CastSpell.StartSpellFromProc(...)`.
- `Character.DoDeath()`.
- `Character.DamageShieldTaken(...)`.
- `Stats.AddStatusEffect(...)` and `Stats.RemoveStatusEffect(...)`.

### P0 — raw amount, mitigation, overkill, resisted are not populated

`CombatEvent` includes `RawAmount` and `Mitigated` (`mod/src/Events/CombatEvent.cs:26-33`),
and docs/web stats consume those fields. `CombatEventBuilder.CreateDamageEvent`
only sets `Amount` and `DamageType` (`mod/src/Hooks/CombatEventBuilder.cs:46-75`).
Damage hooks retain incoming/raw parameters only in optional debug dictionaries;
they do not put them into the event contract.

Impact: web mitigation and defensive metrics are structurally present but will be
zero or inferred from final amount only. Overkill and resisted flags are also
schema-only for now.

### P0 — JSON file export from the mod is not implemented

The architecture and log-format docs describe mod-side JSON export and summary
statistics, but no mod exporter exists. Current export appears to be web-side
session export only. This is acceptable if live WebSocket remains primary, but
the docs should stop presenting mod export as implemented.

## Bugs and correctness risks

### High — actor registry is never cleared between sessions

`ActorRegistry.Clear()` exists and its comment says to call it when starting a
new session (`mod/src/Registry/ActorRegistry.cs:134-145`). `IActorRegistry.Clear`
is not called anywhere in `mod/src`.

Impact:

- Actor IDs continue increasing across sessions instead of being session-local.
- Actor data cached at first registration can become stale across long play
  sessions or after character changes.
- Pet `masterId` remains missing if the pet was first seen before its master;
  the registry never repairs it later (`mod/src/Registry/ActorRegistry.cs:83-98`).

Recommendation: inject `IActorRegistry` into the session/broadcast composition
and clear it at session start, before the first event of the new session is
resolved. Add a regression test that creates two sessions and verifies IDs reset
and master relationships can be resolved in the new session.

### High — context finalizers can pop an outer context they did not push

`DoSkillPatch`, `DoSkillNoChecksPatch`, `ResolveSpellPatch`, and
`DeliverDamagePatch` all return early from prefix when required data is null, but
the finalizer unconditionally calls `CombatContext.PopAbility()`.

Examples:

- `DoSkillPatch.Prefix` returns when `_skill == null`, finalizer still pops
  (`mod/src/Hooks/DoSkillPatch.cs:20-42`).
- `ResolveSpellPatch.Prefix` returns when `__instance.spell == null`, finalizer
  still pops (`mod/src/Hooks/ResolveSpellPatch.cs:20-43`).

Impact: if a null/invalid nested ability method executes while an outer ability
context is active, the finalizer can remove the outer context and misattribute
subsequent damage.

Recommendation: use Harmony `__state` to record whether the prefix pushed, then
pop only when `__state` is true. Add context-stack tests that simulate nested
prefix/finalizer calls with null inner data.

### High — auto-started sessions queue damage before `combatStart`

Damage hooks emit the damage event before notifying the session manager
(`mod/src/Hooks/DamageMePatch.cs:191-194`; the other damage hooks follow the same
pattern). When that first damage starts a session, `SessionManager.StartSession`
emits synthetic `combatStart` afterwards (`mod/src/Session/SessionManager.cs:80-95`,
`mod/src/Session/SessionManager.cs:158-170`).

Impact: the WebSocket client can receive a `sessionStart` message followed by a
batched event list where the first damage event precedes `combatStart`. This
contradicts the chronological contract in `docs/LOG_FORMAT.md:111-134` and makes
first-hit handling order-dependent.

Recommendation: notify/start the session before enqueueing the triggering combat
event, or move automatic session detection into the emitter/broadcaster path so
session state is established before listeners see the event. Add a broadcaster or
session integration test for first-event ordering.

### High — WebSocket binds to all interfaces by default

`WebSocketServer.Start()` uses `ws://0.0.0.0:{port}` and logs LAN URLs
(`mod/src/Server/WebSocketServer.cs:41-52`, `mod/src/Server/WebSocketServer.cs:63-82`).

Impact: live combat/session data is available to any host that can reach the
machine on that port. This is surprising for a local analyzer and is not needed
for the default browser-on-same-machine workflow.

Recommendation: default to loopback (`127.0.0.1`). Add an explicit
`AllowLanConnections` or `BindAddress` config option for users who want LAN
streaming, with a warning in config/docs. Consider an origin/token check if LAN
mode remains supported.

### Medium — status-effect tracker misses common overloads

`AddStatusEffectPatch` hooks only the 4-parameter overload
`Stats.AddStatusEffect(Spell, bool, int, Character)`
(`mod/src/Hooks/AddStatusEffectPatch.cs:14-18`). Current main and playtest also
have 3-parameter and 5-parameter overloads. The playtest decompile contains many
3-parameter call sites, including spell group effects and raid auras.

Impact: DoT/HoT attribution can fail for effects applied through the unpatched
overloads, and future lifecycle events would miss these effects unless every
overload is handled.

Recommendation: patch all relevant `AddStatusEffect` overloads. For overloads
without explicit caster, use current `CombatContext` and/or `StatusEffect.Owner`
where reliable; otherwise emit attribution debug info instead of pretending the
source is known.

### Medium — status lifecycle hooks track attribution only

`AddStatusEffectPatch` and `RemoveStatusEffectPatch` update `EffectTracker`, but
do not emit buff/debuff apply/refresh/fade events. The docs explicitly list those
events as not implemented, while the schema exposes them.

Recommendation: add lifecycle event builders separate from `EffectTracker`.
Classify buff vs debuff using spell beneficial/harmful data, detect refresh vs
new slot, and include `EffectRef` duration/stacks when available.

### Medium — debug capture allocates in hot damage paths when disabled

Damage hooks construct `Dictionary<string,string>` parameter maps before
`CaptureDebugInfoIfEnabled` decides whether debug capture is needed
(`mod/src/Hooks/DamageMePatch.cs:153-168`; similar pattern in other damage
hooks). `EventEmitter.Emit` also copies the listener list for every event
(`mod/src/Events/EventEmitter.cs:38-58`).

Impact: unnecessary allocations on combat hot paths. Probably tolerable today,
but this matters for raid fights, DoTs, AE ticks, and future healing/status event
volume.

Recommendation: guard debug dictionary construction with a cheap boolean first,
or pass a lazy factory. Keep stack traces and string-heavy diagnostics out of the
normal path. For the emitter, consider a copy-on-write subscriber array if event
rate becomes high.

### Medium — config accepts invalid numeric values

`Port`, `BroadcastInterval`, and `SessionInactivityTimeout` are bound without
acceptable value ranges (`mod/src/Config/ModConfig.cs:82-94`,
`mod/src/Config/ModConfig.cs:133-138`).

Impact: invalid ports, zero/negative broadcast intervals, or negative timeouts
can lead to startup failures, excessive broadcasting, or broken session behavior.

Recommendation: use BepInEx `ConfigDescription` with `AcceptableValueRange<T>`
for numeric settings, and validate event-name lists once at config load.

### Medium — release packaging target hardcodes dependency versions

`ILRepack.targets` copies hardcoded BepInEx/Harmony paths:

- `bepinex.baselib/5.4.20/.../BepInEx.dll`
- `harmonyx/2.16.0/.../0Harmony.dll`

But the project uses floating package versions (`BepInEx.Core` `5.*`, `HarmonyX`
`2.*`) in the csproj.

Impact: Release builds can break or silently use mismatched type-resolution
assemblies after package restore updates. This is especially likely on a clean
machine where those exact versions are not in the NuGet cache.

Recommendation: either pin package versions everywhere or derive ILRepack
reference paths from resolved MSBuild items/package versions. Avoid one copy of
version truth in the csproj and another in the targets file.

### Low — manual stop config description is stale

`ManualSessionStopKey` says it only ends manually-started sessions
(`mod/src/Config/ModConfig.cs:69-74`), but `SessionManager.EndManualSession`
explicitly ends any current session (`mod/src/Session/SessionManager.cs:140-155`).

Recommendation: update the config description; the implementation is likely the
more useful behavior.

## Documentation mismatches

### `docs/ARCHITECTURE.md` overstates implemented mod features

Examples:

- Lists `Stats.HealMe` as an implemented hook (`docs/ARCHITECTURE.md:73-83`),
  but no HealMe patch exists.
- Lists `CastSpell.StartSpell` context, while the mod patches
  `SpellVessel.ResolveSpell` and proc start is not implemented.
- Says the session manager hooks into `GameData.InCombat`
  (`docs/ARCHITECTURE.md:99-104`), but current code is event-driven.
- Describes mod JSON exporter and WebSocket commands (`docs/ARCHITECTURE.md:106-118`),
  which are not present.
- Claims death events are Tier 1 verified (`docs/ARCHITECTURE.md:201-210`), but
  `death` is not emitted.

### `docs/LOG_FORMAT.md` uses snake_case, but the wire format is camelCase

`LOG_FORMAT.md` examples use `damage_skill`, `damage_physical`, `heal_spell`,
`buff_apply`, `combat_start`, and `combat_end` (`docs/LOG_FORMAT.md:111-168`).
The mod and web schemas use camelCase (`damageSkill`, `damagePhysical`,
`healSpell`, `buffApply`, `combatStart`, `combatEnd`).

Recommendation: make camelCase the single documented wire/file format unless a
separate snake_case export format is deliberately introduced.

### `docs/COMBAT_EVENTS.md` references missing `CheckForTrueCombatPatch`

The doc says combat detection is handled by `CheckForTrueCombatPatch`
(`docs/COMBAT_EVENTS.md:535-540`), but no such hook exists in `mod/src/Hooks`.
The current design starts sessions from combat events.

Recommendation: update this doc to match event-driven sessions or implement the
combat-state confirmation hook if it is still required.

## Best-practice research and project implications

### BepInEx plugin basics

BepInEx docs require a `BaseUnityPlugin` annotated with `BepInPlugin`; without
that attribute BepInEx ignores the plugin. They also recommend permanent GUIDs
and note that `BaseUnityPlugin` inherits Unity `MonoBehaviour`, enabling `Awake`,
`Update`, and other Unity lifecycle methods.

Project status: good. The mod follows this shape and disposes/unpatches on
teardown.

Source: https://docs.bepinex.dev/articles/dev_guide/plugin_tutorial/2_plugin_start.html

### Runtime patching with HarmonyX

BepInEx ships with HarmonyX and MonoMod.RuntimeDetour. HarmonyX is
attribute-based and broadly compatible with Harmony’s API.

Project status: good baseline, but patch compatibility reporting should improve.
Most hooks are direct compile-time targets, which is fine for stable methods but
brittle for game-update drift. For playtest/main divergence, Harmony
`Prepare()`/`TargetMethod()` can resolve optional targets once and skip/log when
the method is absent.

Sources:

- https://docs.bepinex.dev/articles/dev_guide/runtime_patching.html
- https://harmony.pardeike.net/articles/patching-auxiliary.html

### Unity threading and networking

Unity states that the Unity API is not thread-safe and should be called from the
main thread. Threads can be useful for network communication, but results must be
synchronized back to the main thread.

Project status: mostly acceptable. The game-state hooks run on Unity’s main
thread. Fleck callbacks can occur off-thread; they should not touch Unity API.
Currently they only send protocol/session data, but session state access is not
synchronized. Keep all future inbound WebSocket commands as main-thread queued
commands consumed from `Plugin.Update`.

Source: https://support.unity.com/hc/en-us/articles/208707516-Why-should-I-use-Threads-instead-of-Coroutines

### BepInEx configuration

BepInEx provides `ConfigFile.Bind` and recommends BepInEx `Paths` for mod-owned
files/config. The API supports acceptable-value descriptions/ranges.

Project status: configuration uses BepInEx correctly, but numeric ranges are
missing and the bind address is not configurable.

Source: https://docs.bepinex.dev/articles/dev_guide/plugin_tutorial/4_configuration.html

### Packaging and distribution

Thunderstore packages require root-level `manifest.json`, `README.md`, and a
256x256 PNG `icon.png`; dependencies are declared in `{team}-{package}-{version}`
format. Project constraints correctly prohibit distributing game DLLs or
decompiled proprietary source.

Project status: csproj references game DLLs with `<Private>false>`, and
`.gitignore` excludes `mod/lib/*.dll`, `reference/game-source/*`, and
`reference/game-downloads/`. If publishing, keep package semver distinct from the
mod’s four-part BepInEx/System.Version build version if needed.

Source: https://wiki.thunderstore.io/mods/creating-a-package/

## Recommended architectural improvements

### 1. Establish a compatibility manifest at startup

Add a small `HookCompatibilityReporter` that records each hook target, whether it
was found/applied, and the main/playtest method signature expected. Emit one
startup block in the BepInEx log.

Why: Erenshor updates change game scripts. A compatibility report turns silent
missing patches into actionable evidence and makes support logs useful.

Implementation direction:

- Keep strongly typed `[HarmonyPatch]` for stable methods.
- Use `Prepare()`/`TargetMethod()` with `AccessTools` only for optional or
  version-divergent hooks.
- Add unit/reflection tests against available reference game assemblies or
  decompiled source metadata without committing proprietary DLLs.

### 2. Split hook capture from event classification

Current hooks both capture game facts and choose final event types. This is why
context can identify Backstab while the emitted event remains `damagePhysical`.

Create a testable classifier service that takes:

- raw game method (`DamageMe`, `MagicDamageMe`, `HealMe`, etc.),
- source/target actor types,
- current ability/effect/proc context,
- game result values,
- from-player/critical/resist/absorb flags,

and returns the semantic `EventType`, amount fields, flags, and ability metadata.

Why: the mod can keep hot Harmony patches thin while the classification policy is
unit-tested without Unity objects.

### 3. Make session state the first consumer of combat events

Do not require every hook to remember to call `SessionManager.OnCombatEvent`
after emitting. Centralize session detection so the event bus/broadcaster cannot
observe a combat event before the session state is valid.

Why: prevents first-hit ordering bugs and reduces duplicated hook boilerplate.

### 4. Treat actor/effect registries as session-scoped

Actor and effect registries are conceptually session state. Clear them at session
start/end and make that lifecycle explicit.

Why: session-local IDs are easier for the web app to reason about, avoid stale
cached names/classes/master IDs, and prevent memory growth across long game
sessions.

### 5. Make networking local-first and command-safe

Default WebSocket bind address to loopback. If inbound commands are added later,
parse them into a command queue and execute game-affecting work only in
`Plugin.Update`.

Why: protects users by default and keeps Unity API access on the main thread.

### 6. Keep public contracts generated or cross-tested

The project currently has three contract sources: C# event records/enums, web Zod
schemas, and Markdown docs. They already disagree in places.

Recommendation:

- Add parity tests that compare C# serialized enum names against web schema
  values.
- Update Markdown from the actual protocol or add tests that validate examples.
- Mark schema-only event types explicitly until emitted.

## Suggested implementation priority

1. Fix session-scoped actor registry clearing.
2. Fix ability-context push/pop balancing with Harmony `__state`.
3. Fix first-event `combatStart` ordering.
4. Lock down WebSocket default binding to loopback with explicit LAN opt-in.
5. Update stale docs to match the current implementation.
6. Add healing capture (`Stats.HealMe` overloads) and status lifecycle events.
7. Patch all `AddStatusEffect` overloads needed for DoT/HoT attribution.
8. Populate `rawAmount`, `mitigated`, `overkill`, `resisted`, and pet/proc flags.
9. Add proc/resonance capture via `CastSpell.StartSpellFromProc`.
10. Add death, resource, interrupt, reflect, and avoidance capture.
11. Add startup hook compatibility reporting.
12. Remove hot-path debug allocations.
13. Fix Release ILRepack dependency version drift.

## Tests to add before fixes

- `ActorRegistry` lifecycle: starting a new session clears actors and resets IDs.
- Context stack balancing: null inner skill/spell/projectile prefix does not pop
  an outer context.
- Auto-start ordering: first emitted combat event produces `combatStart` before
  damage in event order.
- WebSocket config: default bind address is loopback; LAN mode must be explicit.
- AddStatusEffect overload coverage: 3-, 4-, and 5-parameter overloads register
  or emit lifecycle events as expected.
- Healing classification: direct spell heal, HoT tick, lifesteal, natural regen,
  and mana-heal paths map to distinct event types.
- Mitigation math: raw amount, final amount, mitigated amount, absorb/miss/resist
  branches, and overkill.
- Proc/resonance context: `StartSpellFromProc` sets `ability.procSource` and
  `flags.resonating` without losing the triggering skill/spell context.
- Documentation parity: `LOG_FORMAT.md` examples deserialize with the web Zod
  schema and match the mod serializer naming policy.

## Bottom line

The mod is a good damage-capture foundation and the recent playtest fixes address
real combat relevance and SimPlayer skill attribution regressions. It is not yet
a complete combat log implementation. The next work should first harden session,
context, networking, and contract correctness, then expand event-family coverage
from the already-identified Erenshor game methods.
